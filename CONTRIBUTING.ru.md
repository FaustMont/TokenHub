# Участие в разработке TokenHub

[English](CONTRIBUTING.md) | [简体中文](CONTRIBUTING.zh-CN.md) | [日本語](CONTRIBUTING.ja.md) | Русский

TokenHub включает Go-бэкенд, административную консоль Next.js, смоук-тесты SDK на Node.js, каталог моделей YAML и файлы развёртывания Docker Compose. В этом руководстве рассматриваются локальная разработка, проверка изменений, опциональные рабочие процессы для ИИ-агентов и подготовка Pull Request.

## Структура репозитория

| Путь | Назначение |
| --- | --- |
| `backend/` | Go HTTP API, персистентность, маршрутизация, аутентификация, администрирование и тесты бэкенда |
| `frontend/` | Административная консоль Next.js и React |
| `sdk/` | Смоук-тесты Node.js для OpenAI-совместимого API и эндпоинтов политик безопасности |
| `data/model-catalog.yaml` | Отслеживаемый исходный каталог моделей |
| `deploy/` | Шаблоны развёртывания и окружения Docker Compose |
| `docs/` | Документация на английском, упрощённом китайском, японском и русском языках |

## Локальная разработка

Для локальной разработки требуются Go 1.26 и Node.js 20 или новее. Docker и Docker Compose требуются только для проверок контейнеров и развёртывания.

Запустите полный стек локальной разработки из корня репозитория:

```bash
./start.sh
```

Чтобы запускать компоненты раздельно, запустите бэкенд из `backend/`:

```bash
TOKENHUB_CORS_ALLOWED_ORIGINS=http://localhost:3000 go run ./cmd/tokenhub
```

Запустите административную консоль из `frontend/`:

```bash
npm ci
npm run dev
```

Запускайте смоук-тесты SDK из `sdk/` только когда доступен совместимый бэкенд и настроены необходимые переменные окружения:

```bash
npm ci
npm run test:deepseek
npm run test:anthropic-messages
npm run test:security-policy
```

## Руководящие принципы внесения изменений

- Сохраняйте изменения сфокусированными и не затрагивайте не относящийся к задаче код.
- Добавляйте или обновляйте тесты при изменении поведения бэкенда. Отдавайте предпочтение внутрипроцессным имитационным (fake) серверам HTTP или SMTP перед внешними сетевыми зависимостями.
- Сохраняйте совместимость для OpenAI-совместимых эндпоинтов `/v1`, если только изменение явно не обновляет контракт.
- Никогда не фиксируйте в коммитах учётные данные, локальные файлы `.env`, базы данных, сгенерированные резервные копии или журналы выполнения.
- Синхронизируйте изменения переменных окружения в соответствующих примерах, файлах Compose, `start.sh` и документации по развёртыванию.
- Поддерживайте синхронизацию общей пользовательской документации на английском, упрощённом китайском, японском и русском языках.
- Сохраняйте `data/model-catalog.yaml` под версионным контролем. Не коммитьте другие файлы данных времени выполнения.

## Проверка и валидация

Во время итераций запускайте наиболее узкий релевантный тест, а перед открытием Pull Request — полный набор применимых проверок.

Проверки бэкенда из `backend/`:

```bash
gofmt -w path/to/changed.go
go test ./...
go vet ./...
```

Проверки фронтенда из `frontend/`:

```bash
npm ci
npm run lint
npm run typecheck
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

Набор смоук-тестов браузера запускает изолированный фронтенд Next.js, Go-бэкенд, моковый апстрим провайдера и временную базу данных SQLite. Он не требует реальных учётных данных или предварительно запущенного стека TokenHub.

Для изменений Docker или развёртывания выполните рендеринг конфигурации Compose при наличии Docker:

```bash
docker compose --env-file deploy/.env.example \
  -f deploy/docker-compose.yml config
```

Выполняйте `git diff --check` для каждого изменения. Сообщайте о любых проверках, которые не удалось запустить, и отделяйте новые сбои от сбоев, уже присутствовавших в базовой ветке.

## Опциональные рабочие процессы разработки с ИИ-агентами

TokenHub предоставляет два подключаемых рабочих процесса для изменений с помощью ИИ:

| Рабочий процесс | Выбирайте для |
| --- | --- |
| [`fast-dev`](docs/development/workflows/fast-dev.md) | Небольших, чётко ограниченных изменений с низким уровнем риска, которые не затрагивают публичные API, персистентность, аутентификацию или авторизацию, развёртывание или поведение нескольких компонентов |
| [`feature-dev`](docs/development/workflows/feature-dev.md) | Важных функций, изменений, видимых пользователю или затрагивающих несколько компонентов, изменений публичных API или моделей данных, чувствительных к безопасности задач, изменений развёртывания, масштабных рефакторингов или архитектурных решений |

Активируйте процесс, указав его имя в запросе, например `Используйте fast-dev для этого изменения.` Без явного указания агент следует стандартным инструкциям репозитория. Если `fast-dev` перестаёт подходить, агент запрашивает подтверждение перед переключением на `feature-dev`. Выбор рабочего процесса не даёт разрешения на коммиты, отправку (push), открытие Pull Request, слияние или другие внешние операции записи.

Инструкции для агентов см. в [AGENTS.md](AGENTS.md#optional-development-workflows).

## Pull Requests

- Составляйте заголовок и каждую секцию описания на английском языке.
- Используйте заголовок в стиле Conventional Commits на английском языке: `<type>[optional scope][!]: <short summary>`.
- Длина заголовка не должна превышать 72 символов, используйте повелительное наклонение в нижнем регистре и не ставьте точку в конце.
- Заполняйте каждый раздел [шаблона Pull Request](.github/pull_request_template.md). Объясняйте пропущенные или неприменимые проверки.
- Описывайте влияние на совместимость API, безопасность, базу данных, окружение, развёртывание, выкатку и откат при необходимости.
- По умолчанию создавайте готовый к ревью Pull Request. Используйте черновик (Draft) только по прямому запросу.
