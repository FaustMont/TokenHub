# Руководство тимлида по внедрению LLM API

Язык: [English](../team-leader-guide.md) | [简体中文](../zh-CN/team-leader-guide.md) | [日本語](../ja/team-leader-guide.md) | Русский

Это руководство предназначено для тимлидов, которые помогают приложениям вызывать утверждённые большие языковые модели через проектные API-ключи TokenHub.

## Зона ответственности тимлида

| Область | Что контролировать |
| --- | --- |
| Проект | Владеть границами для участников, ключей, квот и атрибуции затрат |
| Участники | Добавить владельца приложения или разработчика в панель участников проекта |
| API-ключи | Выдавать ключи в рамках проекта, которому должны принадлежать использование и затраты |
| Модели | Убедиться, что ключ видит нужный список моделей |
| Отчёты | Просматривать статистику по участнику, проекту, модели и центру затрат |

## Межкомандная работа

Проект может быть связан с несколькими командами. **Основная команда** проекта остаётся единственной подотчётной командой для владения по умолчанию, атрибуции затрат и ответственности за согласование. Владелец проекта также остаётся одним конкретным пользователем. Привязка другой команды предоставляет доступ; она не копирует API-ключи проекта, разрешения на модели, квоту, бюджет или политику маршрутизации.

Каждая привязанная команда имеет одну проектную роль:

| Роль команды в проекте | Действующее разрешение |
| --- | --- |
| `viewer` | Просматривать проект и его разрешённые отчёты |
| `developer` | Доступ наблюдателя плюс выпуск ключа проекта, принадлежащего текущему пользователю |
| `maintainer` | Доступ разработчика плюс управление проектом, участниками и ключами, разрешённое ролью пользователя в консоли |

Прямое членство в проекте и каждая привязанная роль команды объединяются детерминировано: `owner` > `maintainer` > `developer` > `viewer`. Пользователь, входящий в несколько привязанных команд, получает наивысшую роль. Администраторы управляют основным и дополнительным членством пользователя в **Управлении пользователями**. Существующие однокомандные проекты мигрируют в режиме совместимости, который сохраняет доступ для их тимлида без предоставления нового доступа обычным пользователям той же команды; администратор может заменить эту роль совместимости в Деталях проекта.

В **Пространствах проектов** выберите проект и используйте **Связанные команды** для добавления команды, изменения её роли или удаления. Изменения доступа вступают в силу при следующем запросе. К пользователям могут быть назначены только активные команды; отключение связанной команды немедленно прекращает предоставление доступа её проектной ролью. Основная команда не может быть удалена до назначения другой основной команды, последняя связанная команда не может быть удалена, а команда, на которую ссылается проект или пользователь, не может быть удалена.

API управления предоставляет те же операции:

| Метод | Эндпоинт | Назначение |
| --- | --- | --- |
| `GET` | `/api/admin/projects/{project_id}/teams?limit=50&offset=0` | Список связанных команд с пагинацией |
| `POST` | `/api/admin/projects/{project_id}/teams` | Привязать `{ "team_id": "...", "role": "viewer|developer|maintainer" }` |
| `PATCH` | `/api/admin/projects/{project_id}/teams/{team_id}` | Изменить роль связанной команды |
| `DELETE` | `/api/admin/projects/{project_id}/teams/{team_id}` | Удалить не-основную и не-последнюю связь команды |

## Выпуск ключа проекта

1. Создайте или выберите проект в **Пространствах проектов**.
2. Нажмите на проект и добавьте владельца приложения в правую панель участников.
3. Откройте **Управление ключами** и создайте ключ в рамках этого проекта.
4. Ограничьте ключ моделями и квотой, необходимыми приложению.
5. Проверьте ключ с помощью `GET /v1/models`.
6. Передайте ключ владельцу приложения через ваш внутренний процесс работы с секретами.

## Проверка доступных моделей

```bash
curl --request GET \
  --url "http://localhost:8080/v1/models" \
  --header "Authorization: Bearer PROJECT_API_KEY" \
  --header "Content-Type: application/json"
```

Возвращаемые значения `data[].id` — это ID моделей, доступных для использования в приложении.

## Проверка вызовов чата

```bash
curl --request POST \
  --url "http://localhost:8080/v1/chat/completions" \
  --header "Authorization: Bearer PROJECT_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "model": "gpt-4.1-mini",
    "messages": [
      {"role": "user", "content": "Write a concise project onboarding checklist."}
    ],
    "stream": false
  }'
```

## Проверки управления

| Проверка | Почему это важно |
| --- | --- |
| Владелец проекта | Использование и затраты должны иметь чёткого владельца |
| Роль участника | Только доверенные участники проекта должны выпускать или ротировать ключи |
| Область моделей | Ключ должен открывать только те модели, которые нужны приложению |
| Квота | Квота и параллелизм должны соответствовать ожидаемому трафику |
| Журналы | Неудачные вызовы должны отслеживаться по `request_id` |

## Распространённые ошибки

| Код | Действия тимлида |
| --- | --- |
| 401 | Убедитесь, что приложение использует активный ключ проекта |
| 403 | Проверьте членство в проекте и разрешённую область моделей |
| 429 | Проверьте квоту, параллелизм и лимиты ключа/проекта |
| 503 | Попросите администратора проверить маршруты и состояние провайдера |
| 500 | Используйте `request_id` в Журналах запросов для анализа ошибки вышестоящего сервиса |
