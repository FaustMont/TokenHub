# Бенчмаркинг производительности

TokenHub включает два взаимодополняющих уровня бенчмаркинга. Блэк-бокс бенчмарки тестируют HTTP-эндпоинт, совместимый с OpenAI, и могут сравнивать TokenHub с другим шлюзом. Внутрипроцессные Go-бенчмарки изолируют затраты на маршрутизацию и управление TokenHub и фиксируют аллокации. Ни один из уровней не обращается к реальному провайдеру моделей.

## Что означают числа

Блэк-бокс раннер сообщает достигнутые запросы в секунду, процент успешных вызовов, байты ответа, сквозную задержку P50/P95/P99 и время до первого байта (TTFT) при потоковой передаче. Он также сообщает **расчётные накладные расходы шлюза**:

```text
max(0, сквозная задержка клиента - настроенная задержка фиктивного вышестоящего сервиса)
```

Эта оценка включает HTTP-транспорт и шум планировщика. Это не внутренний таймер шлюза и его нельзя напрямую сравнивать с бенчмарком, исключающим JSON-сериализацию или HTTP-вызовы. В частности, опубликованные микросекундные накладные расходы Bifrost измеряются с конкретными исключениями; используйте одинаковый внешний раннер и вышестоящий сервис для справедливого сравнения продуктов.

Каждый JSON-результат записывает сценарий, коммит, timestamp, версию Go, операционную систему, архитектуру, модель процессора и его количество, а также системную память. Намеренно исключены API-ключи, имена хостов, имена пользователей и локальные пути.

## Сборка инструмента

Из корня репозитория:

```bash
mkdir -p .tmp
(cd backend && go build -o ../.tmp/tokenhub-benchmark ./cmd/tokenhub-benchmark)
```

Инструмент предоставляет шесть команд:

- `mocker`: детерминированные эндпоинты Chat Completions, Responses, Embeddings и SSE, совместимые с OpenAI.
- `gateway`: автономный in-memory TokenHub плюс детерминированный вышестоящий сервис, для базового дымового теста TokenHub без конфигурации.
- `run`: HTTP-нагрузка с фиксированным параллелизмом или фиксированной скоростью с прогревом и уникальными промптами, исключающими кэширование ответов.
- `check`: сравнение с базовой линией, совместимой со сценарием, с использованием мягкого бюджета производительности.
- `summarize-go`: конвертация повторяющегося стандартного вывода Go-бенчмарка в медианные JSON-метрики.
- `check-go`: сравнение внутренних метрик `ns/op`, `B/op` и `allocs/op` с отслеживаемой базовой линией.

Для быстрого дымового запуска только TokenHub запустите автономный шлюз в одном терминале. Ключ синтетический, существует только в in-memory базе данных бенчмарка и всё равно передаётся через окружение, а не аргумент командной строки:

```bash
TOKENHUB_BENCHMARK_API_KEY=thk_benchmark_local \
./.tmp/tokenhub-benchmark gateway \
  --listen 127.0.0.1:18080 \
  --model benchmark-model \
  --upstream-latency 5ms
```

Затем используйте `run` против `http://127.0.0.1:18080`. Отслеживаемый `benchmarks/baselines/tokenhub-local-smoke.json` был получен таким образом из медианного по пропускной способности результата пяти запусков.

## Запуск детерминированного вышестоящего сервиса

```bash
./.tmp/tokenhub-benchmark mocker \
  --listen 127.0.0.1:18081 \
  --latency 5ms \
  --response-bytes 1024 \
  --stream-chunks 8 \
  --chunk-interval 1ms
```

Настройте оба шлюза с маршрутом `benchmark-model`, перенаправляющим к `http://127.0.0.1:18081/v1`. Дайте каждому шлюзу локальный бенчмарковый API-ключ. Mocker также может внедрять детерминированные сбои с помощью `--failure-every` для тестирования переключения при отказе.

## Сравнение TokenHub и Bifrost

Запустите каждый шлюз на одной иначе незанятой машине, используя одинаковый класс базы данных и настройки телеметрии. Избегайте одновременного запуска обоих измеряемых шлюзов, когда они конкурируют за CPU. Запускайте каждую цель несколько раз и чередуйте их порядок.

```bash
export TOKENHUB_BENCHMARK_TOKENHUB_URL=http://127.0.0.1:8080
export TOKENHUB_BENCHMARK_BIFROST_URL=http://127.0.0.1:8082
export TOKENHUB_BENCHMARK_TOKENHUB_API_KEY=YOUR_TOKENHUB_BENCHMARK_KEY
export TOKENHUB_BENCHMARK_BIFROST_API_KEY=YOUR_BIFROST_BENCHMARK_KEY
export TOKENHUB_BENCHMARK_MODEL=benchmark-model

./benchmarks/run-comparison.sh
```

Скрипт чередует порядок целей на протяжении пяти запусков и записывает пронумерованные файлы JSON и Markdown в `output/benchmarks/`, который намеренно игнорируется Git. Измените количество повторений, длительность, прогрев, параллелизм, директорию результатов, ожидаемую задержку вышестоящего сервиса и профиль развёртывания базы данных/телеметрии с помощью переменных `TOKENHUB_BENCHMARK_*`, определённых в начале скрипта.

Для потоковых тестов, Responses, Embeddings или тестов насыщения с фиксированной скоростью вызывайте раннер напрямую:

```bash
TOKENHUB_BENCHMARK_API_KEY=YOUR_LOCAL_BENCHMARK_KEY \
./.tmp/tokenhub-benchmark run \
  --label tokenhub-stream-c32 \
  --base-url http://127.0.0.1:8080 \
  --model benchmark-model \
  --protocol chat \
  --stream \
  --mode concurrency \
  --concurrency 32 \
  --warmup 5s \
  --duration 30s \
  --upstream-latency 13ms \
  --upstream-ttft 5ms \
  --json output/benchmarks/tokenhub-stream-c32.json \
  --markdown output/benchmarks/tokenhub-stream-c32.md
```

В режиме фиксированной скорости задайте `--mode rate --rate N --concurrency 0`. Сбой `load_generator_saturated` означает, что клиент достиг `--max-in-flight`; `load_generator_missed_schedule` означает, что клиент не смог отправить запросы с нужной частотой. Ни то, ни другое не является ответом шлюза, и запуск, содержащий любой из них, не должен использоваться как прошедшее сравнение задержки.

Для потокового запуска `--upstream-latency` означает общую длительность ответа вышестоящего сервиса, а `--upstream-ttft` — время до первого байта вышестоящего сервиса. При настройках mocker по умолчанию общая длительность — начальная задержка плюс `stream-chunks * chunk-interval` (5 мс + 8 * 1 мс = 13 мс). Указание обоих не позволяет оценкам накладных расходов для полного ответа и TTFT приписывать детерминированную доставку фрагментов шлюзу.

## Запуск матрицы внутренних бенчмарков

```bash
./benchmarks/run-internal.sh
```

Матрица охватывает Chat Completions, Responses, потоковую передачу, переключение при отказе, SQLite, изолированную персистентность аудита полезных нагрузок с идентичными контрольными значениями 32 КБ, прямой рендеринг малых/крупных записей аудита, метрики и трассировку с захватом полезных нагрузок и без. Используется `ReportAllocs`, поэтому стандартный вывод Go включает `ns/op`, `B/op` и `allocs/op`. Скрипт агрегирует повторные образцы по медиане и завершается с ненулевым кодом, если любая метрика превышает `benchmarks/internal-budget.json` (25% по времени, 15% по байтам или 10% по аллокациям от базовой линии).

PostgreSQL является опциональным, чтобы обычные тестовые запуски не обращались к общему сервису. Каждый тестовый случай выполняется в транзакции, которая откатывается, поэтому повторные случаи не сохраняют маршруты или строки аудита:

```bash
TOKENHUB_BENCHMARK_POSTGRES_URL='postgres://tokenhub:password@127.0.0.1:5432/tokenhub_benchmark?sslmode=disable' \
./benchmarks/run-internal.sh
```

Используйте одноразовую пустую базу данных. Настройка и миграции находятся за пределами измеряемого интервала, тогда как персистентность запросов включена.

Внутренние базовые линии специфичны для профиля: по умолчанию используется `benchmarks/baselines/internal/sqlite.json`, тогда как запуск с `TOKENHUB_BENCHMARK_POSTGRES_URL` использует `sqlite-postgresql.json`. Создавайте или намеренно обновляйте базовую линию только из чистой зафиксированной ревизии:

```bash
TOKENHUB_BENCHMARK_UPDATE_BASELINE=1 ./benchmarks/run-internal.sh
```

Также задайте URL PostgreSQL при обновлении этого профиля. Проверки базовых линий завершаются с ошибкой, если набор бенчмарков, версия Go, ОС, архитектура, модель/количество CPU или системная память отличаются.

## Проверка и обновление базовой линии

Отслеживаемый бюджет в `benchmarks/budget.json` требует не менее 99,9% успешных запросов, не менее 90% от базовой пропускной способности, не более 15% регрессии средней задержки и не более 20% регрессии P99. Эти допуски снижают количество ложных сбоев от джиттера общих раннеров, при этом всё ещё выявляя существенные изменения. Отслеживаемые локальные базовые линии охватывают Chat, Responses, потоковую передачу и вызванное переключение при отказе.

```bash
./.tmp/tokenhub-benchmark check \
  --baseline benchmarks/baselines/tokenhub-local-smoke.json \
  --current output/benchmarks/tokenhub-local-smoke.json \
  --budget benchmarks/budget.json \
  --markdown output/benchmarks/budget-check.md
```

Проверка отклоняет результаты, у которых отличается схема, протокол, режим потоковой передачи, режим нагрузки, уровень нагрузки, модель, размер запроса, настроенная задержка вышестоящего сервиса или профиль среды выполнения/оборудования. Обновляйте отслеживаемую базовую линию только после намеренного изменения производительности, используя стабильную машину и не менее пяти повторных запусков. Сохраняйте медианный запуск, описывайте оборудование и команду в pull request и никогда не добавляйте учётные данные или одноразовые локальные результаты.

Чтобы проверить все четыре сценария, поместите текущие результаты с теми же именами файлов, что в `benchmarks/baselines/*.json`, в одну директорию, затем запустите:

```bash
./benchmarks/check-suite.sh output/benchmarks/current
```

Отпечаток сценария также включает длительность, прогрев, таймаут, максимальное количество запросов в полёте, размер ответа, форму потока и профиль развёртывания, описывающий настройки базы данных и телеметрии. Сравнение завершается с ошибкой, если любое из них отличается или если генератор нагрузки отбрасывает предложенные запросы.

## Интерпретация сравнения

Считайте запуск недействительным, если процент успешных запросов существенно отличается, генератор нагрузки насыщается, любой шлюз повторяет попытки разное количество раз, или нагрузка на CPU и память отличается. Сравнивайте пропускную способность при фиксированном параллелизме, задержку при фиксированном предложенном RPS, TTFT при потоковой передаче и аллокации по отдельности. Одно максимальное число пропускной способности не объясняет стоимость гарантий TokenHub по персистентности, аудиту, маршрутизации, метрикам и трассировке.
