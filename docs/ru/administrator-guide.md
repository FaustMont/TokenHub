# Руководство администратора

Язык: [English](../administrator-guide.md) | [简体中文](../zh-CN/administrator-guide.md) | [日本語](../ja/administrator-guide.md) | Русский

Это руководство предназначено для платформенных администраторов, специалистов по безопасности и владельцев инфраструктуры, эксплуатирующих TokenHub в качестве корпоративного AI-шлюза.

## Область ответственности администратора

| Область | Ответственность |
| --- | --- |
| Каналы провайдеров | Настройка вышестоящих подключений, импорт инвентаря моделей и поддержка фактических затрат провайдера |
| Каталог моделей | Выбор из встроенного каталога, создание внешних API-моделей, выбор начальных маршрутов провайдера и установка единых клиентских цен |
| Политики маршрутизации | Тонкая настройка маппинга провайдеров, приоритета, весов, области проекта и стратегии отработки отказов |
| Проекты и команды | Определение границ владения для ключей, квот и атрибуции затрат |
| Источники идентификации | Настройка OAuth или OIDC-провайдеров входа для корпоративной аутентификации |
| Безопасность и аудит | Просмотр журналов запросов, административных событий, ротации ключей и изменений политик |

## Порядок производственной настройки

1. Настройте хотя бы один источник идентификации и сохраните контролируемый аккаунт администратора.
2. Добавьте вышестоящий провайдер, например `OpenAI Production`, `Azure East US` или `Internal Model Gateway`. Перед сохранением используйте **Тест подключения** для проверки Base URL и API Key, изучите измеренную задержку ответа, затем импортируйте модели, которые провайдер может обслуживать.
3. Зафиксируйте фактические входные, кэш-читаемые и выходные затраты на каждую импортированную модель провайдера для аудита.
4. Создайте внешние модели для предоставления приложениям и установите их единые клиентские цены.
5. Добавьте маршруты от каждой внешней модели к одной или нескольким импортированным моделям провайдера.
6. Создайте команды, проекты, центры затрат и политики квот по умолчанию.
7. Проверьте поток с помощью Model Playground и журналов запросов.
8. Проверьте атрибуцию использования перед массовой выдачей ключей.

Провайдеры Anthropic используют аутентификацию `x-api-key` по умолчанию. Если вышестоящий сервис, совместимый с Anthropic, требует `Authorization: Bearer`, откройте вкладку **Дополнительно** провайдера, оставьте **Тип провайдера** установленным в **Claude / Anthropic** и выберите **Authorization Bearer** в разделе **Аутентификация Anthropic**. TokenHub выводит любой из заголовков из зашифрованного API Key провайдера и отправляет только выбранный заголовок аутентификации; не дублируйте учётные данные в пользовательских заголовках.

## Диагностика в Model Playground

Откройте **Model Playground** из консоли для проверки модели через те же адаптеры маршрутизации и провайдера, которые используются шлюзовым трафиком. Каждый ход ассистента сохраняет компактную диагностическую сводку: режим доставки, измеренное шлюзом время до первого токена (TTFT), скорость генерации, общая длительность, входные токены полного контекста, выходные токены, расчётная стоимость, локальное время завершения и ID запроса. Разверните **Диагностика** для просмотра миллисекундных временных меток и фактических деталей ответа. Сессии остаются на текущей странице браузера, пока не будут явно экспортированы.

TokenHub передаёт унифицированный формат SSE-событий в Playground. Если выбранный вышестоящий сервис поддерживает потоковую передачу, TTFT измеряется от приёма шлюзом до первого дельты контента, а скорость генерации рассчитывается за интервал от первого до последнего контента. Если вышестоящий сервис поддерживает только буферизованные ответы, TokenHub автоматически переключается в буферизованный режим, помечает TTFT как неприменимое и сообщает сквозную скорость генерации вместо искусственного измерения первого токена. Остановка запроса сохраняет частичный текст и помечает кандидата как отменённого; авторитетные счётчики токенов отображаются только когда провайдер их возвращает.

Повторный запуск хода ассистента создаёт ещё одного кандидата для этого хода и удаляет последующие ходы, чтобы новая ветка не могла молча использовать устаревший контекст. Смена моделей по умолчанию запускает новую сессию; сохранение существующего контекста требует явного выбора. Управление параметрами следует объявленным `supported_parameters` выбранной модели, поэтому Playground не отправляет элементы управления, которые каталог моделей считает неподдерживаемыми.

Все разрешённые пользователи Playground могут видеть производительность, использование, ID запроса и детали своих ответов. Провайдер, ресурс, ID запроса вышестоящего сервиса и детали маршрутизации для каждой попытки видны только ролям с разрешением на чтение маршрутизации. Стоимость помечается как расчётная, поскольку использует настроенную цену внешней модели, а не счёт вышестоящего сервиса.

## Политики безопасности контента

Откройте **Политики безопасности > Безопасность контента** для создания политик для всех или выбранных проектов. Политика может сочетать сопоставление по ключевым словам или регулярным выражениям, обнаружение конфиденциальных данных и опциональный детектор модели Qwen3Guard. Элементы обнаружения оцениваются совместно, и побеждает наиболее строгое совпадающее действие: `block` над `mask` над `audit`. Изменения вступают в силу при сохранении.

Детерминированные детекторы работают внутри TokenHub. Перед вызовом настроенного детектора Qwen3Guard TokenHub заменяет конфиденциальные значения, уже совпавшие с локальными правилами `mask`, на `[REDACTED]` в копии только для детектора, поэтому эти исходные значения не отправляются в сервис модели. Текст, не совпавший с локальным правилом маскирования, всё равно отправляется в сервис, настроенный в `TOKENHUB_GUARDRAIL_MODEL_URL`. Развёртывайте этот сервис только в рамках утверждённой границы данных и проверяйте его транспорт, ведение журналов и контроль хранения; TokenHub не может управлять копиями, сохраняемыми удалённым сервисом. Оставив URL пустым, вы предотвращаете вызовы модели и применяете настроенное поведение каждого элемента обнаружения модели при недоступности.

Обнаружение конфиденциальных данных включает размеченные или структурно проверенные примеры: номера удостоверений личности Китая, мобильные номера материкового Китая, email-адреса, номера банковских карт, учётные данные и закрытые ключи, имена людей, адреса и даты рождения. Валидаторы — проверки дат, контрольные суммы удостоверений личности и проверки Луна — снижают количество ложных срабатываний для числовых значений. Используйте **Тест политики** с репрезентативными положительными и отрицательными образцами перед широким включением политики.

Применение на стороне запроса охватывает `/v1/chat/completions`, `/v1/responses`, `/v1/responses/compact` и `/v1/messages`, включая запросы из Model Playground. TokenHub проверяет обычный видимый пользователю текст перед маршрутизацией к провайдеру. Структурированные аргументы инструментов, значения JSON-полей, специфичный для кода анализ и ответы провайдера не проверяются в этой версии. Проверка не устанавливает отдельного ограничения размера текста; настроенный лимит тела запроса по-прежнему применяется. Детерминированное обнаружение также применяет взвешенные по сложности бюджеты совокупной работы и количества находок, поэтому патологические комбинации длинного текста, дорогостоящих выражений или плотных совпадений маскирования завершаются с HTTP 503 `guardrail_evaluation_budget_exceeded` вместо монополизации процессора или памяти; обычные длинные контексты с умеренным набором правил остаются поддерживаемыми.

Когда политика блокирует запрос, совместимые API возвращают HTTP 403 с кодом `guardrail_blocked`. Детали ошибки включают `categories`, `reason_codes` и `policy_matches`; каждое совпадение политики идентифицирует политику, элемент обнаружения, тип детектора, категорию и код причины. Ответ также включает `request_id` для корреляции в аудите. Оригинальный совпавший текст не включается в детали ошибки. Model Playground представляет ту же информацию о политике и причине, чтобы администраторы могли сообщить о воспроизводимой находке вместо того, чтобы видеть только «Запрос заблокирован политикой безопасности контента».

## Владение API-ключами и атрибуция использования

При выдаче API-ключа выберите фактического пользователя в поле **Пользователь-владелец**. Выдавший остаётся в метаданных аудита, но использование ключа атрибутируется его владельцу. Платформенные администраторы могут выбрать любого активного пользователя; тимлиды — активного пользователя из своей команды; обычные пользователи могут назначать ключи только себе.

Каждая новая запись использования делает снимок атрибутированного пользователя, поэтому последующие изменения владения или удаление ключа не перезаписывают зафиксированную историю. Записи, созданные до появления этого поля, используют только атрибуцию, доказуемую из неизменяемой записи использования или истории запросов; в противном случае они остаются `unknown`. Унаследованные квотные бакеты сохраняются как неатрибутированная каноническая история и никогда не назначаются молча текущему владельцу при обновлении. Индивидуальный рейтинг отдельно показывает использованные ключи и текущие не-отозванные ключи в собственности.

Страница **Использование** отдельного ключа использует сохранённый ID ключа как точную границу для трендов, разбивок по моделям и ошибкам и деталей запросов. Ссылки на ротацию носят информационный характер и не объединяют использование предшественника и преемника. Его текущие дневные и месячные карточки квоты ключа используют UTC-бакеты и разрешают те же глобальные лимиты, лимиты проекта, команды и ключа, которые используются для проверки пропуска ключей шлюзом. Совокупные пользовательские квоты применяются отдельно и не включены в это представление ключа. Платформенные администраторы дополнительно получают разбивки производительности провайдера и ресурса; другие роли сохраняют существующую видимость деталей запросов в ограниченной области, а стоимость провайдера ограничена платформенными администраторами.

## Панель суточного использования

Откройте раздел **Использование**, чтобы увидеть текущее суточное использование над более длительным сводным отчётом. Дневной блок показывает токены за сегодня, запросы, расчётную стоимость, чтения кэша и таблицы по типу токена, модели, проекту и API-ключу. Платформенные администраторы также видят таблицы провайдера и ресурса провайдера; другие роли получают только оставшиеся ограниченные измерения. Тимлиды также видят использование участников своей команды, а роли управления видят атрибуцию по центру затрат.

Граница дня берётся из **Системные настройки > Базовые настройки шлюза > Часовой пояс панели**. Используйте IANA-часовой пояс, например `UTC`, `Asia/Shanghai` или `America/New_York`. TokenHub хранит этот параметр централизованно, поэтому все администраторы видят одно и то же суточное окно, а панель сбрасывается в полночь этого часового пояса. Представление использования обновляет дневной блок каждые 30 секунд пока открыто.

## Только-читаемый доступ к затратам для локальных агентов

Не давайте агенту автоматизации сессию администратора или API-ключ для вызова моделей лишь для сбора статистики. Создайте специализированные аналитические учётные данные `tha_`, по возможности ограничьте их одним проектом и отзывайте независимо. [Руководство по API стоимости токенов для агентов](agent-token-cost-api.md) документирует жизненный цикл учётных данных, фильтры, агрегацию, схемы JSON/CSV, пагинацию снимков, инкрементальные водяные знаки, поведение аудита и лимиты запросов.

## Лимиты RPM и TPM на уровне ключей

Каждый API-ключ может иметь опциональные лимиты запросов в минуту (RPM) и токенов в минуту (TPM). Незаданное или `null` значение наследует применимые глобальные политики, проекта и команды. Значение `0` не добавляет специфичного для ключа ограничения, но не может обойти ограничение верхнего уровня, тогда как положительное значение добавляет специфичное для ключа ограничение. Когда применяются несколько положительных лимитов, TokenHub применяет наиболее строгий. Отключение ключа отклоняет каждый запрос независимо от значений лимита.

RPM потребляется до вызова провайдера. TPM резервируется в тот же момент из расчётного входного и максимального выходного количества запроса; текстовые запросы без явного максимума резервируют 4096 выходных токенов. После завершения запроса резервирование закрывается по итоговым токенам провайдера или по промпту плюс токены завершения при недоступности итога. Кэшированные и рассуждающие токены уже включены в эти итоги и не добавляются повторно. Неудачные или прерванные запросы возвращают неиспользованное резервирование.

Превышенный лимит возвращает HTTP 429 с `api_key_rpm_exceeded` или `api_key_tpm_exceeded`, плюс `Retry-After` и соответствующие заголовки `X-RateLimit-Limit-*`, `X-RateLimit-Remaining-*` и `X-RateLimit-Reset-*`. Минутные бакеты поддерживаются базой данных. PostgreSQL разделяет применение между экземплярами TokenHub; SQLite сохраняет поддерживаемое поведение одного бэкенда. Метрики раскрывают только короткую хешированную ссылку на ключ, никогда не полный API-ключ.

Для высококонкурентных развёртываний операторы могут настроить `TOKENHUB_BILLING_REDIS_URL`. При настройке TokenHub использует Redis для высоконагрузочного пути приёма: резервирования RPM/TPM на минуту для API-ключа и пользователя плюс аренды параллелизма ключа и пользователя. База данных остаётся надёжным биллинговым реестром для дневных и месячных счётчиков, записей использования, журналов запросов, аудиторских следов и идемпотентности расчётов. Настроенный Redis-эндпоинт требуется при запуске; оставьте переменную пустой, чтобы сохранить путь приёма на основе базы данных. Развёртывания Docker Compose могут добавить `deploy/docker-compose.redis.yml` для запуска опционального Redis-компонента, управляемого тем же Compose-проектом.

## Совокупные пользовательские квоты

Платформенные администраторы и тимлиды настраивают совокупные пользовательские лимиты в **Управление затратами > Политики квот**, выбирая `user` в качестве области и активный ID пользователя в `scope_id`. Тимлид может управлять политиками только для пользователей из своих команд; платформенные администраторы могут управлять любым активным пользователем. Селектор пользователей перечисляет пользователей, доступных текущему администратору, а таблица политик показывает текущее суточное и месячное потребление. Пользовательские политики поддерживают полный квотный диапазон: RPM, TPM, суточные и месячные запросы, токены и стоимость, плюс максимальный параллелизм.

TokenHub разрешает атрибутированного пользователя в том же порядке, что используется для учёта использования: `owner_user_id` API-ключа, затем устаревшие метаданные ключа `created_by`, затем `owner_user_id` проекта. Каждый ключ, атрибутированный этому пользователю, потребляет одни и те же пользовательские бакеты, включая ключи в разных проектах. Ротация, отзыв, удаление или замена ключа не сбрасывает эти счётчики, поскольку бакеты принадлежат пользователю, а не ключу.

Пользовательские лимиты применяются наряду с применимыми лимитами API-ключа, проекта, команды и глобальными лимитами. Положительные лимиты сохраняют существующее поведение наиболее строгого значения, тогда как пользовательские счётчики остаются совокупными, а не становятся расчётом на ключ. Пользовательский максимальный параллелизм удерживается в дополнение к эффективной аренде параллелизма ключа, поэтому ни одно ограничение не может обойти другое.

Приём резервирует пользовательские запросы и расчётные токены перед любым вызовом провайдера. Общая транзакция расчёта согласовывает резервирование с фактическим измеренным использованием и использует ID запроса в качестве постоянного маркера идемпотентности для буферизованных, потоковых, образовательных и фоновых вызовов Responses. Фоновые задания сохраняют состояние своего резервирования, поэтому отмена, восстановление после перезапуска и остановившиеся воркеры не могут рассчитать его дважды. PostgreSQL использует транзакционные консультативные блокировки и блокировки строк между репликами; SQLite использует сериализацию транзакций одного бэкенда. Заблокированный запрос возвращает HTTP 429 до вызова провайдера с `details.scope` установленным в `user`. Нагрузки аудита, оповещения и метрики сохраняют ограниченную область без раскрытия ID пользователя или секрета API-ключа.

## Доступность каталога провайдеров

TokenHub хранит последний известный рабочий каталог провайдеров в базе данных. При каждом запуске бэкенда он проверяет и загружает настроенный локальный `provider-catalog.json`, затем атомарно заменяет снимок базы данных. Обычные запросы **Каналов провайдеров** только читают снимок базы данных. Явное обновление администратора загружает последний каталог `PublicProviderConf`, применяет те же проверки полноты и атомарно заменяет снимок только при успешной проверке. При сбое вышестоящего запроса или проверки TokenHub откатывается к настроенному локальному каталогу. Если этот откат также не удаётся, обновление возвращает ошибку и TokenHub продолжает использовать последний известный рабочий снимок. Ответы обновления идентифицируют выбранный источник как `upstream-provider-catalog` или `local-provider-catalog`.

## Обновление токена OAuth Codex

Для активных аккаунтов OpenAI Codex Subscription с сохранённым токеном обновления TokenHub проверяет учётные данные при запуске бэкенда и затем каждую минуту. Он обновляет токен доступа только при истечении в течение пяти минут. Аренда учётных данных на основе базы данных гарантирует, что кластерное развёртывание выполняет только одно обновление для аккаунта. В **Каналы провайдеров > Дополнительно > Квота подписки**, **Обновить токен** позволяет администратору обновить один аккаунт по требованию. Используйте для восстановления, а не для повторных нажатий: ответ обновления может ротировать токен обновления, и TokenHub автоматически сохраняет возвращённую замену. Если OpenAI сообщает об аннулированном токене обновления, TokenHub помечает аккаунт как требующий повторной авторизации, останавливает запланированные попытки обновления и показывает администратору запрос на повторную авторизацию.

### Локальный вывод Kronk

Выберите **Kronk** в **Каналах провайдеров** для подключения независимо запущенного Kronk Model Server. Base URL по умолчанию: `http://127.0.0.1:11435/v1`. Оставьте токен приложения пустым, когда аутентификация Kronk отключена; иначе TokenHub отправляет сохранённый секрет только как `Authorization: Bearer <token>`. Тест подключения проверяет `/v1/liveness`, `/v1/readiness` и `/v1/models` отдельно, чтобы доступный процесс, готовый сервис и используемые локальные модели оставались различимыми состояниями.

Выборщик моделей обнаруживает живой инвентарь из `GET /v1/models` и сохраняет каждый полный ID модели Kronk, включая `/`, `:` и суффиксы квантования. Импортируйте выбранный инвентарь, затем создайте внешнее стандартное имя в **Каталоге моделей** и сопоставьте его с ID Kronk в **Политиках маршрутизации**. Повторные импорты идемпотентны. Успешное последующее обнаружение помечает отсутствующие модели Kronk недоступными без удаления их инвентаря или маршрутов; неудачное обнаружение оставляет существующую конфигурацию без изменений.

Маршруты Kronk поддерживают OpenAI-совместимые Chat Completions, Responses и Embeddings, включая SSE-потоковую передачу. TokenHub продолжает применять свои политики аутентификации клиентов, изоляции проектов, квот, аудита, маршрутизации и отработки отказов. Он никогда не пересылает заголовок `Authorization` вызывающего к Kronk и не раскрывает сохранённый токен Kronk в ответах управления, нагрузках аудита, журналах или ответах с ошибками вышестоящего сервиса.

## Обработка атрибуции Claude Code

Claude Code может размещать блок текста атрибуции в начале массива `system` Anthropic Messages. Блок содержит клиентские метаданные, которые могут варьироваться между запросами и мешать стороннему вышестоящему сервису повторно использовать иначе стабильный префикс промпта.

Каждый провайдер имеет настройку `claude_code_attribution_policy`. Новые официальные провайдеры Anthropic по умолчанию используют `preserve`, тогда как провайдеры, известные как неофициальные, по умолчанию используют `strip` для лучшего повторного использования кэша стороннего префикса. Пользовательские эндпоинты Anthropic с неизвестным происхождением по умолчанию используют `preserve`. Существующие провайдеры без этой настройки также продолжают сохранять блок. `strip` удаляет блок только когда первый элемент верхнего уровня `system` имеет `type: "text"` и его текст начинается точно с `x-anthropic-billing-header:`. Строковые значения `system`-промптов, последующие блоки, ведущие пробелы и другие типы блоков никогда не удаляются.

Ресурсы провайдера по умолчанию наследуют политику провайдера и могут переопределить её через `options.claude_code_attribution_policy`, установив `preserve` или `strip`. Опускание этой опции ресурса восстанавливает наследование. TokenHub применяет эффективную политику отдельно для каждой попытки маршрута, поэтому резервный ресурс получает исходный запрос и применяет свою настройку. Нагрузки аудита также сохраняют исходный запрос. `POST /v1/messages/count_tokens` продолжает подсчитывать исходный запрос, поскольку не выбирает конкретный ресурс провайдера.

## Конвергенция отпечатка Codex

Ресурсы OpenAI Codex Subscription могут сходить идентификаторы устройства и сессии клиента перед отправкой запроса Responses или Compact в вышестоящий сервис. Настройте **Конвергенцию отпечатка Codex** в ресурсе аккаунта. Режим по умолчанию `session` выводит стабильные идентификаторы установки и сессии на уровне аккаунта, выводя при этом стабильный ID потока из оригинальной клиентской сессии. `device` изменяет только ID установки, `full` также сходит всех клиентов к одному потоку, а `off` передаёт идентификаторы клиента без изменений.

Политика перезаписывает соответствующие поля в заголовках протокола Codex и `client_metadata`, включая встроенные `x-codex-turn-metadata`, из одного предварительно вычисленного набора ID, чтобы запрос оставался внутренне согласованным между повторными попытками. В режимах `session` и `full` исходные идентификаторы родителя, ответвления и поворота родителя удаляются, поскольку они принадлежат пространству имён потока до перезаписи. Стабильные значения выводятся из ID ресурса провайдера и не раскрывают сохранённые учётные данные OAuth. Настройка хранится как `options.codex_fingerprint_mode`; значение по умолчанию `session` представлено отсутствующей опцией. Установите режим в `off` для возврата к сквозному поведению.

## Кредиты сброса использования Codex

Для активного аккаунта OpenAI Codex Subscription откройте **Каналы провайдеров**, отредактируйте провайдера и разверните **Дополнительно > Квота подписки**. Карточка аккаунта показывает авторитетное количество доступных кредитов сброса и ближайший срок истечения, сообщённый OpenAI. **Сбросить окно использования** открывает второе подтверждение перед тем, как потратить один невозвратный кредит; оно сбрасывает подходящие окна использования Codex, но не изменяет тарифный план ChatGPT. Завершённая или идемпотентно повторённая операция обновляет как квоту, так и детали кредитов сброса.

Состояние идемпотентности сброса хранится как записи `AdminResource` вида `codex-quota-reset-operations` в существующей таблице admin-resources, поэтому эта функция не требует миграции схемы. Успешные и неудачные записи сохраняются и автоматически не удаляются, поскольку предотвращают повторное потребление другого кредита при воспроизведении; включите их в нормальное хранение базы данных и резервное копирование. При обновлении сохраните базу данных. Запись `pending` или `unknown` блокирует другой сброс для того же аккаунта, отображается в консоли после перезапуска и может быть повторена только с тем же ключом идемпотентности, ожидаемым счётчиком и ID кредита до тех пор, пока OpenAI не вернёт окончательный результат.

## Инвентарь провайдеров, каталог моделей и публикация

TokenHub разделяет жизненный цикл модели на три зоны управления:

| Зона управления | Значение |
| --- | --- |
| **Каналы провайдеров** | Вышестоящие подключения и их импортированный инвентарь моделей. Создание провайдера на основе каталога требует выбора хотя бы одной модели, но импорт инвентаря сам по себе никогда не делает его доступным для клиентов. Пользовательские провайдеры могут создаваться пустыми и пополняться после доступности вышестоящего подключения. |
| **Каталог моделей** | Только внешние модели, формирующие API-контракт для приложений. Создание начинается с выбора шаблона из встроенного эталонного каталога или чистой пользовательской модели, затем выбора одной или нескольких импортированных моделей провайдера для начальных маршрутов. Его цены — единые клиентские цены, независимо от того, какой маршрут провайдера обслуживает запрос. |
| **Политики маршрутизации** | Управление маппингом провайдеров внешней модели и тонкая настройка приоритета, весов, области проекта, распределения трафика и стратегии отработки отказов. |

Ответственности остаются разделёнными: сначала добавьте провайдера и импортируйте инвентарь; затем выберите одну из встроенных эталонных моделей, создайте её внешний контракт, выберите хотя бы один начальный маршрут провайдера и установите её единую внешнюю цену. Выбранный шаблон предварительно заполняет имя, возможности, контекст и предлагаемые цены, которые можно изменить перед сохранением. После создания добавляйте, изменяйте или удаляйте маппинги только в Политиках маршрутизации. Каталог моделей сохраняет только-читаемую сводку вышестоящего сервиса и открывает Политики маршрутизации, отфильтрованные по выбранной внешней модели; действие «Настроить маршруты» в списке провайдеров открывает полное рабочее пространство Политик маршрутизации для добавления новых маппингов. Например, администратор может опубликовать внешнюю модель `DeepSeek`, маршрутизируя её к `OpenAI Production / gpt-4.5`. Одна модель провайдера может поддерживать несколько внешних псевдонимов, и одна внешняя модель может маршрутизироваться к нескольким провайдерам.

Цены модели провайдера представляют фактическую стоимость вышестоящего сервиса и используются для внутреннего аудита. Цены каталога моделей представляют единую внешнюю цену для оценок клиентского биллинга, учёта квот, метрик и отчётов об использовании. Маршрут выбирает вышестоящую реализацию, но не изменяет внешнюю цену.

Когда в Каналах провайдеров, Каталоге моделей или Политиках маршрутизации нет настроенных данных, консоль показывает одинаковое трёхшаговое руководство по настройке: импортируйте инвентарь провайдера, создайте внешнюю модель из встроенного каталога, затем настройте маршрутизацию. Основное действие всегда указывает на самое раннее незавершённое требование, чтобы администраторы не попадали в форму, которую ещё нельзя заполнить.

Публикация и работоспособность в реальном времени — это разные состояния. Членство в `GET /v1/models` требует активной внешней `Model`, хотя бы одного активного `ModelRoute` и доступа по API-ключу при настроенном белом списке моделей. Оно не меняется когда провайдер или ресурс провайдера временно неработоспособен. Работоспособность влияет на то, может ли быть обслужен запрос, и отображается отдельно в каталоге и диагностике маршрутизации. Отключение внешней модели удаляет её из `GET /v1/models`, сохраняя её маппинги для последующей повторной публикации.

## Пользовательские заголовки вышестоящих запросов

В **Каналах провайдеров** добавьте фиксированные пользовательские заголовки запросов в настройках подключения провайдера или в расширенных настройках ресурса провайдера. Заголовки провайдера являются значениями по умолчанию; заголовок ресурса с тем же именем без учёта регистра переопределяет значение провайдера для этой фактической попытки маршрутизации. Это делает безопасным переключение при отказе между аккаунтами: TokenHub пересчитывает эффективные заголовки для каждого выбранного ресурса. Например, установите `User-Agent: TokenHub-Custom-Client/1.0` в области провайдера и переопределите `X-Tenant` для отдельных ресурсов.

Эффективные заголовки применяются единообразно к тестам подключения, пользовательскому обнаружению моделей, OpenAI-совместимым Chat Completions, Responses, Embeddings и Images (включая потоковую передачу и редактирование изображений), нативным Anthropic Messages и запросам Gemini. Адаптеры Azure OpenAI и OpenAI Codex не поддерживают пользовательские заголовки, поскольку управляют собственной идентичностью протокола.

Отмечайте учётные данные или клиентские токены как конфиденциальные. TokenHub шифрует конфиденциальные значения в состоянии покоя, маскирует их в ответах управления и предварительных просмотрах и исключает значения заголовков из снимков аудита. При редактировании сохранённой конфиденциальной строки оставьте замаскированное значение без изменений или пустым для сохранения секрета; удалите строку для её очистки. Не конфиденциальные значения остаются видимыми для администраторов.

TokenHub отклоняет заголовки аутентификации, учётные данные API-ключей и куков, заголовки перенаправления идентификации, заголовки, принадлежащие протоколу, такие как `Content-Type`, `Content-Length`, `Host`, `Anthropic-Version`, `Anthropic-Beta`, `OpenAI-Organization` и `OpenAI-Project`, плюс hop-by-hop и транспортные заголовки. Имена заголовков должны быть корректными и уникальными без учёта регистра; значения должны быть непустыми и не содержать управляющих символов, отклоняемых HTTP-транспортом. Итоговая объединённая конфигурация может содержать не более 32 заголовков, с именами до 128 байт, каждое значение до 4 КБ и 16 КБ суммарно. Устаревшие данные, нарушающие эти правила, сообщаются с `header_validation_errors` и не применяются к вышестоящим запросам до исправления.

## Политики маршрутизации моделей

Консоль администратора настраивает одну стратегию маршрутизации для всей внешней модели. Откройте карточку модели и выберите вкладку стратегии; активная вкладка объясняет лучший вариант использования, фактическое поведение выбора, значение параметров и конкретный пример. Настройте параметры провайдера, показанные для этой стратегии, затем выберите **Применить стратегию**. Политика и каждый параметр провайдера сохраняются атомарно, поэтому модель никогда не работает с частично обновлённой конфигурацией.

Для маршрутизации с фиксированным соотношением введите относительный вес рядом с каждым провайдером. Два провайдера с весами 75 и 25 отображают целевые доли 75% и 25%. Адаптивная маршрутизация использует те же значения как базовые веса и динамически корректирует эффективные доли. Режимы качества, стоимости и сбалансированный выставляют только свои соответствующие оценки. Все эти стратегии помещают подходящих провайдеров в один пул распределения трафика. Последовательное переключение при отказе — единственный режим, использующий порядок провайдеров; перетащите строки для установки первого, второго и последующих вариантов.

| Стратегия | Поведение |
| --- | --- |
| `priority_weighted` | Использует настроенные веса как целевое соотношение трафика по маршрутам с одинаковым приоритетом. Например, веса 75 и 25 целятся в разбивку 75:25 по репрезентативному объёму запросов. |
| `adaptive` | Начинает с настроенных весов и корректирует эффективные веса, используя вызванные попытки за последние 15 минут. Маршрут начинает адаптацию после 5 образцов; недавний процент успешных запросов и задержка успешных запросов влияют на его долю с ограниченными корректировками для предотвращения голодания или крайних сдвигов. |
| `quality` | Всегда пробует первой наивысшую оценку качества, вес используется только для разрешения одинаковых оценок. |
| `cost` | Всегда пробует первым наивысшую оценку эффективности затрат. Более высокая оценка означает более дешёвый, предпочтительный провайдер. |
| `priority_only` | Использует список провайдеров как строгий порядок основных/резервных и не распределяет нормальный трафик. |
| `balanced` | Сохраняет устаревшее поведение, используя `weight + quality score + cost score` как эффективный вероятностный вес. Новые конфигурации должны обычно использовать вместо него фиксированное соотношение или адаптивную маршрутизацию. |

Детали подключения провайдера и ограничения проекта остаются специфичными для маршрута. Редактирование одного маршрута провайдера изменяет его вышестоящую модель, область проекта, настройку сессионного закрепления или статус; общая стратегия, вес и оценки редактируются в политике модели. `all` делает маршрут доступным для каждого проекта, `include` ограничивает его выбранными проектами, а `exclude` делает его доступным для каждого проекта, кроме выбранных. Область проекта оценивается до распределения трафика и переключения при отказе, а отображаемые доли трафика пересчитываются по подходящим провайдерам.

Для частной границы проекта создайте внутренний маршрут провайдера с областью `include` и выберите частные проекты. Создайте соответствующий внешний маршрут провайдера с областью `exclude` и выберите те же проекты. Частные проекты тогда смогут использовать только внутренний маршрут, тогда как другие проекты продолжат использовать внешнего провайдера.

Область проекта маршрута также управляет обнаружением моделей: `GET /v1/models` включает внешнюю модель только когда проект вызывающего API-ключа имеет хотя бы один активный подходящий маршрут, в дополнение к обычным проверкам белых списков модели и API-ключа.

### Ограниченные политики маршрутизации

Используйте **Ограниченные политики** для привязки независимой политики маршрутизации к глобальному шлюзу, проекту или API-ключу. TokenHub разрешает ровно одну эффективную политику в следующем порядке: API-ключ, затем проект, затем глобальная. Нахождение привязки более высокого приоритета заканчивает разрешение, даже когда эта политика отключена, конфликтует или не оставляет подходящего кандидата; маршрутизатор завершается отказом и никогда не откатывается к более низкой области. Только одна политика может быть привязана к данной цели, тогда как непривязанные определения могут подготавливаться без влияния на трафик.

Доступ к модели оценивается до маршрутизации. Проекты и API-ключи поддерживают режимы доступа `inherit` и `restricted`. Ограниченный список пересекается с каждым списком верхнего уровня, поэтому API-ключ не может расширить доступ проекта; ограниченный пустой список запрещает каждую модель. Для совместимости записи, созданные до существования режимов доступа с пустым режимом и пустым списком, продолжают наследовать. `GET /v1/models` применяет ту же эффективную область доступа и требует маршрута, разрешённого эффективной политикой маршрутизации.

Ограниченная политика может ограничивать имена моделей, провайдеров, ресурсы провайдеров, требуемые теги маршрута, регионы ресурсов и среды ресурсов, и может переопределять стратегию маршрутизации. Настройте теги в маршрутах моделей и метаданные региона/среды в ресурсах провайдеров. Существующие области проекта на уровне маршрута пересекаются с этими ограничениями. Распределение трафика, закрепление сессий/кэша, полуоткрытое восстановление и переключение при отказе выполняются только после фильтрации и никогда не могут добавить исключённый маршрут обратно в пул кандидатов. Это делает внутреннюю политику безопасно завершающейся отказом вместо молчаливого перехода к внешнему провайдеру.

Панель предварительного просмотра/симуляции принимает проект, API-ключ и модель и отображает эффективную политику, решение о доступе, выбранный маршрут и безопасную причину разрешения/исключения для каждого кандидата. Сбои политики используют диагностические коды, такие как `routing_policy_unavailable`, `routing_policy_conflict` и `routing_policy_no_candidate`, не раскрывая учётные данные. Журналы запросов записывают `routing_policy_id`, `routing_policy_scope` и `routing_policy_priority`; общие операции создания/обновления/удаления политик и явные операции привязки/отвязки также записывают события аудита администратора.

API управления использует общий CRUD ресурсов на `/api/admin/resources/routing-policies`, плюс `POST /api/admin/routing-policies/{id}/bind`, `POST /api/admin/routing-policies/{id}/unbind` и `POST /api/admin/routing-policies/simulate`. Та же принудительная логика применяется к OpenAI-совместимым запросам моделей, Anthropic Messages, генерации изображений и playground администратора.

## Восстановление ресурса провайдера

Ресурс провайдера, сбои которого превышают `TOKENHUB_RESOURCE_FAILURE_THRESHOLD` раз подряд, паркуется: он перестаёт получать трафик и входит в период охлаждения. Восстановление автоматическое и не требует действий администратора.

| Фаза | Поведение |
| --- | --- |
| Запаркован | Ресурс исключён из маршрутизации на `TOKENHUB_RESOURCE_COOLDOWN_SECONDS` |
| Полуоткрыт | После истечения периода охлаждения ровно один запрос пропускается как пробный; каждый другой запрос всё ещё отклоняется |
| Восстановлен | Успешное достижение вышестоящего сервиса пробным запросом очищает автоматический выключатель, сбрасывает счётчик сбоев и поднимает оповещение `provider_resource_recovered` |
| Повторно запаркован | Неудачный пробный запрос немедленно вооружает следующий период охлаждения, удваивая его каждый раз до `TOKENHUB_RESOURCE_COOLDOWN_MAX_SECONDS` |

Только успех самого пробного запроса закрывает автоматический выключатель. Запрос, уже находившийся в обработке при срабатывании автоматического выключателя, не может его закрыть, независимо от его результата. Что учитывается, определяется тем, что сбой вышестоящего сервиса доказал об ресурсе, а не статусом, данным вызывающему. Клиент, отключившийся в середине потока, политический отказ, неподдерживаемая модель, запрос, отклонённый вышестоящим сервисом как некорректный, и всё остальное, относящееся к запросу, а не к аккаунту, не считается ни за, ни против ресурса: они не добавляют сбоя, но и не сбрасывают ни одного, поэтому чередующийся паттерн сбой/отключение всё равно срабатывает. Отклонённые учётные данные, неоплачиваемый аккаунт, ограничение скорости и любой сбой вышестоящего сервиса считаются против него.

Тестирование ресурса из консоли всё равно немедленно восстанавливает его, когда адаптер поддерживает зондирование, поскольку этот зонд выдаёт реальный вышестоящий запрос. Отключение ресурса остаётся административным переопределением: отключённый ресурс никогда не восстанавливается автоматически, что бы ни сообщал вышестоящий сервис.

## Классификация ошибок вышестоящего сервиса

Сбой вышестоящего сервиса оценивается по трём отдельным вопросам, поскольку один код статуса не может ответить на все: что говорится вызывающему, пробует ли маршрутизатор другого кандидата, и учитывается ли попытка против ресурса провайдера. Некорректный запрос некорректен для каждого провайдера, поэтому он сообщается вызывающему и другой кандидат не пробуется. Отклонённые учётные данные специфичны для одного аккаунта, поэтому запрос переходит дальше и обвиняется аккаунт.

| Вышестоящий сервис | Вызывающий видит | Код ошибки | Другой кандидат | Считается против ресурса |
| --- | --- | --- | --- | --- |
| `400`, `422` | тот же статус | `provider_invalid_request` | Нет | Нет |
| `401`, `403` | `502` | `provider_auth_error` | Да | Да |
| `402` | `502` | `provider_payment_required` | Да | Да |
| `404` | `502` | `provider_model_not_found` | Да | Нет |
| `408` | `504` | `provider_upstream_timeout` | Да | Да |
| `413` | `413` | `provider_invalid_request` | Нет | Нет |
| `429` | `429` с `Retry-After` | `provider_rate_limited` | Да | Да |
| `502`, `503`, `504` | тот же статус | `provider_upstream_unavailable` | Да | Да |
| другой `5xx` | `502` | `provider_upstream_error` | Да | Да |
| другой `4xx` | `502` | `provider_error` | Нет | Нет |

Вышестоящий `401` или `403` не пересылается таким: это означает, что собственные учётные данные шлюза для этого провайдера были отклонены, и вызывающий, прочитав `401`, заключил бы, что его токен TokenHub истёк. По той же причине тело вышестоящего сервиса на эти два скрывается, поскольку провайдеры цитируют отклонённый ключ в нём. Исходный статус записывается как `upstream_status` в каждой попытке маршрута, где оператор может его увидеть.

Каждая попытка маршрута записывает оба: `status_code` — то, что сказано вызывающему, `upstream_status` — то, что ответил провайдер.

## Аудит использования запросов

Каждая строка запроса в **Журналах запросов** включает итоговые токены и внешнюю сумму биллинга. Для администраторов с глобальной операционной видимостью панель деталей также показывает фактическую стоимость провайдера, рассчитанную из выбранной модели провайдера; другие пользователи не получают это поле стоимости. Панель сохраняет разбивку биллинга вышестоящего сервиса при её доступности: кэшированные, кэш-записанные и аудио входные токены, плюс рассуждающие, аудио, принятые предсказания и отклонённые предсказания выходные токены. Провайдеры, не возвращающие поле, отображаются как ноль. Итоги входа и выхода уже содержат свои детальные категории, поэтому не добавляйте детальные значения к итогам повторно.

## Метрики

TokenHub может предоставлять метрики Prometheus на `GET /metrics`. Сбор отключён по умолчанию; установите `TOKENHUB_METRICS_ENABLED=true` для включения. При отключении ничего не собирается и эндпоинт возвращает 404. Эндпоинт всегда аутентифицирует: метрики раскрывают имена моделей, идентификаторы провайдеров и ресурсов, и расходы, поэтому никогда не анонимны. Отправьте `Authorization: Bearer <token>` с помощью `TOKENHUB_METRICS_TOKEN` или токена администратора, когда эта переменная пуста. Рекомендуется специальный токен, чтобы конфигурация скрейпинга не несла учётные данные администратора. Токен, указанный в строке запроса, отклоняется, поскольку он будет захвачен в журналах доступа.

| Метрика | Тип | Значение |
| --- | --- | --- |
| `tokenhub_gateway_requests_total` | счётчик | Логические запросы к API модели. Запрос с переключением при отказе по нескольким кандидатам считается один раз. |
| `tokenhub_gateway_request_duration_seconds` | гистограмма | Сквозная задержка, включая попытки переключения при отказе. Бакеты до 300с. |
| `tokenhub_gateway_route_attempts_total` | счётчик | Физические попытки кандидатов. |
| `tokenhub_gateway_attempt_duration_seconds` | гистограмма | Длительность одной вызванной попытки маршрута. |
| `tokenhub_gateway_routed_requests_total` | счётчик | Логические запросы, сделавшие хотя бы одну попытку кандидата. |
| `tokenhub_gateway_overhead_seconds` | гистограмма | Приблизительные накладные расходы шлюза. |
| `tokenhub_gateway_time_to_first_byte_seconds` | гистограмма | Воспринимаемое клиентом время до первого байта для потоковых запросов. |
| `tokenhub_gateway_stream_interruptions_total` | счётчик | Потоковые запросы, завершившиеся с ошибкой после записи первого байта. |
| `tokenhub_gateway_requests_in_flight` | датчик | Запросы к API модели, обслуживаемые в данный момент. |
| `tokenhub_gateway_tokens_total` | счётчик | Токены по виду: `prompt`, `completion`, `cached`, `cache_write`, `reasoning`. |
| `tokenhub_gateway_cost_usd_total` | счётчик | Единая внешняя оценка биллинга по ценам каталога моделей. |
| `tokenhub_gateway_rate_limit_hits_total` | счётчик | Отклонённые запросы по эффективной области политики и типу лимита. |
| `tokenhub_gateway_trace_completions_total` | счётчик | Завершённые вызовы по тому, что экспорт трассировки с ними сделал. |
| `tokenhub_gateway_trace_spans_total` | счётчик | Спаны по тому, что с ними сделал OTLP-экспортёр. |

Метрики среды выполнения и процесса Go предоставляются вместе с ними.

**Виды токенов не являются разделом и не должны суммироваться.** `prompt` уже содержит токены `cached` и `cache_write`, а `reasoning` — подмножество `completion`. Суммирование видов приводит к двойному счёту.

Примеры полезных PromQL:

```promql
# Средняя глубина переключения при отказе по модели.
sum by (model) (rate(tokenhub_gateway_route_attempts_total[5m]))
/
sum by (model) (rate(tokenhub_gateway_routed_requests_total[5m]))

# 99-й перцентиль накладных расходов шлюза.
histogram_quantile(
  0.99,
  sum by (le, stream) (rate(tokenhub_gateway_overhead_seconds_bucket[5m]))
)
```

## Экспорт трассировок

TokenHub может экспортировать одну трассировку OpenTelemetry на вызов шлюза через OTLP/HTTP. Каждая трассировка — это корневой спан для запроса плюс один спан генерации для каждого кандидата, вошедшего в путь вызова, поэтому переключение при отказе показывает обоих кандидатов с токенами и стоимостью, которую каждый из них потребил. Экспорт отключён по умолчанию.

Установите `TOKENHUB_TRACING_ENDPOINT` в signal-специфичный OTLP URL трассировок, включая полный путь.

Для Langfuse:

```bash
TOKENHUB_TRACING_ENABLED=true
TOKENHUB_TRACING_ENDPOINT=https://cloud.langfuse.com/api/public/otel/v1/traces
TOKENHUB_TRACING_HEADERS="Authorization=Basic $(printf '%s' 'pk-lf-...:sk-lf-...' | base64),x-langfuse-ingestion-version=4"
```

Отображение атрибутов нацелено на модель ingestion Langfuse v4, которая общедоступна для self-hosted развёртываний и является значением по умолчанию для организаций Langfuse Cloud, созданных после 14.04.2026. Self-hosting Langfuse v4 требует ClickHouse 25.12 или новее вместе с PostgreSQL, Redis и хранилищем объектов.

Включение захвата промптов и ответов — это отдельное решение от включения трассировки, и `TOKENHUB_TRACING_CAPTURE_PAYLOADS` отключён по умолчанию.

![Трассировка при переключении при отказе в Langfuse: корневой спан запроса, две неудачные попытки на недоступном аккаунте и генерация, обслужившая его со своим счётчиком токенов и стоимостью](../assets/screenshots/tracing-langfuse-trace-en.png)

![Список трассировок Langfuse, показывающий шлюзовой, playground и отклонённый трафик рядом с возможностью фильтрации по тегу](../assets/screenshots/tracing-langfuse-list-en.png)

Экспорт никогда не задерживает запрос. Завершения ставятся в очередь и превращаются в спаны в отдельной горутине; когда очередь заполнена, завершение сбрасывается, а не ждёт.

## Ценообразование кэша промптов

Каталог моделей принимает опциональные цены кэш-чтения и кэш-записи в USD за 1 миллион токенов. Когда ценообразование кэш-записи не настроено, TokenHub выставляет счёт за токены кэш-записи по обычной входной цене для сохранения устаревших оценок.

Записи использования раскрывают `input_cost_usd`, `cache_read_cost_usd`, `cache_write_cost_usd` и `output_cost_usd` наряду с итоговым `estimated_cost_usd`, чтобы отчёты могли проверить, как была составлена финальная сумма из использования провайдера.

## Восстановление метаданных каталога

Удаление внешней модели удаляет её запись в базе данных и маршруты, но не редактирует `data/model-catalog.yaml` или файл, настроенный через `TOKENHUB_MODEL_CATALOG_FILE`. Запуск бэкенда синхронизирует отслеживаемые метаданные каталога из этого файла снова; администраторы могут вызвать ту же синхронизацию без перезапуска из **Настройки → Базовые настройки → Синхронизировать эталонный каталог моделей**.

## Внешние биллинговые коннекторы

Платформенные администраторы управляют внешними источниками биллинга из **Биллинг затрат**. TokenHub поддерживает `QueryInstanceBill` Aliyun, данные квот NewAPI и совместимые с OneAPI источники логов. Коннектор может быть протестирован, синхронизирован немедленно, запланирован с минутным интервалом, отключён без удаления истории и повторно включён позже.

## Сверка затрат

Платформенные администраторы могут сравнивать синхронизированные счета провайдеров с использованием TokenHub из **Биллинг затрат → Правила сверки затрат**. Правило выбирает один биллинговый коннектор, гранулярность detail/hour/day/month, сопоставляемые измерения, IANA-часовой пояс, одну ISO-валюту, абсолютный и относительный допуски, детальное временное окно, окно задержки биллинга и опциональное расписание.

## Китайские корпоративные источники идентификации

| Feishu | Создать корпоративное самостоятельное приложение, включить веб-авторизацию, зарегистрировать URL обратного вызова, скопировать App ID и App Secret. Предоставить доступ к профилю и корпоративному email при наличии. | Использует Feishu OAuth v2 токен API и разворачивает ответ `data` user-info. ## Email-каналы уведомлений

Каналы уведомлений типа `email` доставляются через SMTP. По умолчанию TokenHub подключается в открытом тексте и переходит на STARTTLS по объявленным возможностям сервера (обычно порт 587). Для почтовых серверов, предоставляющих SMTP только через неявный TLS порт, например 465, установите поле канала `smtp_encryption` в `ssl`, `tls`, `smtps` или `implicit` для открытия подключения с TLS с первого байта. Канал сохраняет другие стандартные поля (`smtp_host`, `smtp_port`, `smtp_username`, `smtp_password`, `smtp_from`, `email_to`).

В форме email-канала консоли администратора селектор **Шифрование SMTP** предлагает `auto` (оппортунистический STARTTLS, устаревшее значение по умолчанию), `starttls` (требуемый STARTTLS, отказ от отправки при неподдержке, порт 587) и `ssl` (неявный TLS с первого байта, порт 465); новые каналы по умолчанию используют `starttls`. Выбор `auto` оставляет `smtp_encryption` неустановленным, сохраняя устаревшее оппортунистическое поведение STARTTLS; только `starttls` и `ssl` записывают поле.
