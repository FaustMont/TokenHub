# API стоимости токенов для агентов

Язык: [English](../agent-token-cost-api.md) | [简体中文](../zh-CN/agent-token-cost-api.md) | [日本語](../ja/agent-token-cost-api.md) | Русский

Версионированный API стоимости токенов для агентов позволяет локальному агенту отчётности или мониторинга читать данные использования TokenHub без сессии администратора, API-ключа для вызова моделей, учётных данных провайдера или ручного экспорта. API работает только на чтение и использует те же записи о запросах, токенах, ошибках и расчётных клиентских затратах, что и представление использования администратора.

## Эндпоинты

| Эндпоинт | Аутентификация | Назначение |
| --- | --- | --- |
| `GET /api/v1/analytics/token-costs` | Аналитические учётные данные | Запрос стоимости токенов на уровне запросов или агрегированных данных в формате JSON или CSV |
| `GET /api/admin/analytics/credentials` | Администратор платформы | Список метаданных аналитических учётных данных |
| `POST /api/admin/analytics/credentials` | Администратор платформы | Создание аналитических учётных данных с однократным раскрытием токена |
| `DELETE /api/admin/analytics/credentials/{id}` | Администратор платформы | Немедленный отзыв аналитических учётных данных |

Аналитические учётные данные начинаются с `tha_`. Они не могут аутентифицироваться для `/v1/models`, эндпоинтов вывода моделей или административных эндпоинтов.

## Создание учётных данных с минимальными привилегиями

Используйте сессию администратора или настроенный токен администратора для создания учётных данных с областью проекта:

```bash
curl -sS https://tokenhub.example.com/api/admin/analytics/credentials \
  -H "Authorization: Bearer $TOKENHUB_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "payments-cost-agent",
    "scope_type": "project",
    "project_id": "prj_payments",
    "expires_at": "2026-12-31T00:00:00Z"
  }'
```

Ответ включает метаданные `credential` и `token`. Скопируйте токен немедленно; последующие ответы списка раскрывают только его префикс и суффикс. Задайте `scope_type` в `organization` и опустите `project_id` только когда агент должен читать весь экземпляр TokenHub. Срок истечения опционален, но рекомендуется.

Сохраните токен в хранилище секретов локального агента:

```bash
export TOKENHUB_ANALYTICS_TOKEN='tha_REPLACE_ME'
```

Отзовите учётные данные, когда агент выведен из эксплуатации или его токен мог быть раскрыт:

```bash
curl -sS -X DELETE \
  https://tokenhub.example.com/api/admin/analytics/credentials/acred_REPLACE_ME \
  -H "Authorization: Bearer $TOKENHUB_ADMIN_TOKEN"
```

## Запрос стоимости на уровне запросов

`from` включительно, `to` исключительно, оба используют RFC 3339. Пропуск обоих выбирает предыдущие 24 часа до начала запроса.

```bash
curl -sS -G https://tokenhub.example.com/api/v1/analytics/token-costs \
  -H "Authorization: Bearer $TOKENHUB_ANALYTICS_TOKEN" \
  --data-urlencode 'from=2026-08-01T00:00:00Z' \
  --data-urlencode 'to=2026-08-02T00:00:00Z' \
  --data-urlencode 'provider_id=prv_openai' \
  --data-urlencode 'model=gpt-4.1-mini' \
  --data-urlencode 'status=success' \
  --data-urlencode 'limit=100'
```

По умолчанию `granularity=request` возвращает одну очищенную строку на запрос шлюза. Строка содержит стабильные ID и метрики, но никогда — предъявленный аналитический токен, секрет API-ключа, учётные данные провайдера, стоимость провайдера, IP-адрес клиента, тело запроса, тело ответа или User-Agent.

## Фильтрация и агрегация

Следующий пример создаёт суточные итоги по проекту, провайдеру, модели и статусу успех/ошибка:

```bash
curl -sS -G https://tokenhub.example.com/api/v1/analytics/token-costs \
  -H "Authorization: Bearer $TOKENHUB_ANALYTICS_TOKEN" \
  --data-urlencode 'from=2026-07-01T00:00:00Z' \
  --data-urlencode 'to=2026-08-01T00:00:00Z' \
  --data-urlencode 'granularity=day' \
  --data-urlencode 'group_by=project,provider,model,status'
```

Используйте `granularity=hour`, `day` или `month` для временных бакетов. Используйте `granularity=none` для итогов без временного бакета. Указание `group_by` без `granularity` также выбирает `none`. `request` нельзя комбинировать с `group_by`.

| Параметр | Значения и поведение |
| --- | --- |
| `from`, `to` | Интервал RFC 3339 `[from, to)`; по умолчанию предыдущие 24 часа |
| `project_id` | Точный ID проекта; учётные данные проекта всегда привязаны к его проекту и получают `403` для другого проекта |
| `user_id` | Точный ID атрибутированного пользователя |
| `api_key_id` | Точный хранимый ID API-ключа, никогда не секрет API-ключа |
| `provider_id` | Точный ID провайдера |
| `model` | Точное внешнее имя модели |
| `status` | `success` для HTTP-статуса ниже 400, или `error` для статуса 400 и выше |
| `granularity` | `request` (по умолчанию), `none`, `hour`, `day` или `month` |
| `group_by` | Разделённые запятыми или повторяющиеся `project`, `user`, `api_key`, `provider`, `model` и `status` |
| `limit` | 1–1000 строк; по умолчанию 100 |
| `cursor` | Непрозрачный `next_cursor` с предыдущей страницы |
| `after` | Непрозрачный зафиксированный `watermark` для инкрементальной выгрузки по последовательности коммитов; нельзя комбинировать с `from` или `cursor` |
| `format` | `json` (по умолчанию) или `csv`; `Accept: text/csv` также выбирает CSV |

Начальные снимки на уровне запросов ограничены 31 днём, а начальные агрегированные снимки — 366 днями. Инкрементальные выгрузки изменений ограничены последовательностью коммитов, поэтому они могут сохранять исходный `from` при продвижении `to` за эти пределы без повторного сканирования исходной истории.

## Схема JSON

Каждый JSON-ответ объявляет `schema_version: "1.0"` и имеет такую форму:

```json
{
  "schema_version": "1.0",
  "object": "token_cost.list",
  "generated_at": "2026-08-02T00:00:01Z",
  "query": {
    "from": "2026-08-01T00:00:00Z",
    "to": "2026-08-02T00:00:00Z",
    "granularity": "day",
    "group_by": ["project", "model"],
    "filters": {"project_id": "prj_payments"},
    "format": "json",
    "limit": 100,
    "dedupe_by": "dedupe_key",
    "checkpoint_by": "commit_sequence",
    "incremental_mode": "snapshot"
  },
  "data": [
    {
      "dedupe_key": "aggregate_f6d6...",
      "bucket": "2026-08-01",
      "project_id": "prj_payments",
      "model": "gpt-4.1-mini",
      "metrics": {
        "request_count": 42,
        "error_count": 2,
        "input_tokens": 120000,
        "cached_input_tokens": 35000,
        "cache_write_input_tokens": 4000,
        "output_tokens": 18000,
        "reasoning_output_tokens": 2500,
        "total_tokens": 138000,
        "estimated_cost_usd": 1.73
      }
    }
  ],
  "has_more": false,
  "watermark": "OPAQUE_WATERMARK"
}
```

`request_count` и `error_count` берутся из журналов запросов шлюза, включая неудачные запросы без записи использования. Метрики токенов и стоимости берутся из записей использования. Счётчики кэша и рассуждений — это детали, уже представленные в итогах входных/выходных данных; не складывайте каждое детальное поле с `total_tokens`. `estimated_cost_usd` — это настроенная внешняя клиентская плата, используемая представлением использования администратора, а не конфиденциальная стоимость провайдера TokenHub.

## Пагинация и инкрементальные выгрузки

Когда `has_more` равно true, вызовите эндпоинт снова с `cursor=next_cursor`. Курсор сохраняет исходные фильтры, `granularity`, `group_by` и интервал снимка, поэтому эти параметры можно опустить. Если они указаны, они должны совпадать с курсором. Верхняя граница снимка остаётся фиксированной, поэтому запросы, поступающие во время пагинации, не смещают последующие страницы.

`watermark` ответа идентифицирует завершённый снимок базы данных. В PostgreSQL новые журналы запросов объединяют свой ID транзакции с постоянным смещением, а обновление присваивает замороженной истории отдельные значения контрольных точек, упорядоченные по времени события. Перезапись истории использует MVCC и не берёт табличную блокировку, останавливающую новые вставки журнала запросов. Водяной знак никогда не продвигается за наибольшую видимую последовательность журнала запросов; после `pg_restore` запуск перебазирует постоянное смещение выше восстановленного максимума, поэтому существующие водяные знаки агента остаются действительными в новом кластере. Контрольная точка также останавливается до старейшей активной транзакции снимка, поэтому более поздние транзакции могут фиксироваться без ожидания общей аналитической строки. SQLite использует транзакционно обновляемую последовательность в рамках существующей модели единственного писателя базы данных. Контрольная точка останавливается до первого совпадающего зафиксированного запроса, чей `occurred_at` находится на уровне или выше `to`, поэтому продвижение `to` не может пропустить уже зафиксированное будущее событие. Водяной знак возвращается даже когда снимок не содержит совпадающих строк. Слейте каждую страницу до тех пор, пока `has_more` не станет false, успешно обработайте строки и только затем зафиксируйте водяной знак в долговечном состоянии агента. Начните следующий запуск с `after=<committed watermark>`:

```bash
curl -sS -G https://tokenhub.example.com/api/v1/analytics/token-costs \
  -H "Authorization: Bearer $TOKENHUB_ANALYTICS_TOKEN" \
  --data-urlencode "after=$TOKENHUB_COST_WATERMARK"
```

Выгрузка `after` устанавливает `query.incremental_mode` в `changes` и возвращает только журналы запросов, чья последовательность коммитов больше зафиксированного водяного знака и не превышает новый снимок. Исходные фильтры и событийное `from` сохраняются, тогда как `to` может продвигаться. Поэтому запрос, зафиксированный поздно, возвращается независимо от того, находится ли его `occurred_at` раньше самого нового события предыдущего водяного знака.

Изменения на уровне запросов используют `request_id` как `dedupe_key`. Агрегированные строки изменений — это дельты по вновь зафиксированным запросам; их ключ идентифицирует начальную зафиксированную контрольную точку, форму запроса, бакет и измерения. Стейджируйте или применяйте каждую страницу по этому ключу, применяйте завершённую дельту ровно один раз и атомарно продвигайте водяной знак. Повторная попытка с тем же зафиксированным водяным знаком сохраняет те же ключи и заменяет стейджированные значения, даже если более новый снимок продвинулся. Изменение фильтров или формы агрегации при повторном использовании водяного знака отклоняется; начните отчёт другой формы с новым снимком `from` и `to`.

## Экспорт CSV

```bash
curl -sS -G https://tokenhub.example.com/api/v1/analytics/token-costs \
  -H "Authorization: Bearer $TOKENHUB_ANALYTICS_TOKEN" \
  -H 'Accept: text/csv' \
  --data-urlencode 'from=2026-08-01T00:00:00Z' \
  --data-urlencode 'to=2026-08-02T00:00:00Z' \
  --data-urlencode 'granularity=hour' \
  --data-urlencode 'group_by=project,provider,model' \
  -o token-costs.csv
```

CSV использует те же фильтры, лимиты, метрики, пагинацию и `dedupe_key`, что и JSON. Метаданные возвращаются в заголовках `X-TokenHub-Schema-Version`, `X-TokenHub-Has-More`, `X-TokenHub-Next-Cursor`, `X-TokenHub-Watermark`, `X-TokenHub-Dedupe-By`, `X-TokenHub-Checkpoint-By` и `X-TokenHub-Incremental-Mode`. Текстовые ячейки, которые могут интерпретироваться как формулы электронных таблиц, получают префикс апострофа.

## Оценка CLI и MCP

| Вариант | Решение | Причина |
| --- | --- | --- |
| Версионированный HTTP + CSV | Поддерживается сейчас | Работает из любого языка, cron-раннера или среды выполнения агента; не требует дополнительного дистрибутива бинарного файла; оставляет аутентификацию и контрольные точки явными |
| Специализированный CLI | Отложено | CLI в основном оборачивал бы HTTP, добавляя работу по установке, обновлению и локальной конфигурации секретов; пересмотреть при запросе интерактивной настройки учётных данных или пакетирования запланированных отчётов |
| MCP-сервер/инструмент | Отложено | MCP добавил бы ещё одну долгоживущую границу доверия и специфичное для хоста развёртывание; пересмотреть когда хосты агентов потребуют обнаружения инструментов или общего управления контрольными точками вместо прямого HTTP |

Любой будущий адаптер CLI или MCP должен принимать только аналитические учётные данные, сохранять семантику курсора/водяного знака, раскрывать ту же версию схемы и никогда не запрашивать сессию администратора или API-ключ для вызова моделей.

## Безопасность и эксплуатация

- Только администраторы платформы могут создавать, перечислять или отзывать аналитические учётные данные.
- Каждый успешный запрос, отклонённый запрос области, недействительный запрос и попытка с недействительными учётными данными записывают событие аудита типа `token_cost_analytics`.
- Аналитические учётные данные и их хэши исключены из ответов запросов и снимков аудита. Храните одноразовый токен как секрет.
- Аналитические чтения используют специализированный небольшой пул соединений, отдельный от основного пула шлюза. Файловый SQLite включает WAL, чтобы читатели не блокировали записи шлюза; PostgreSQL использует независимый аналитический пул. Каждый запрос имеет 10-секундный дедлайн выполнения в дополнение к индексированным путям `created_at` и `(project_id, created_at)`, лимитам диапазона времени и лимитам размера страниц.
- Отзыв вступает в силу при следующем запросе. Ротируйте учётные данные путём создания замены, обновления агента и отзыва старых учётных данных.
- Используйте пагинацию вместо параллельных неограниченных выгрузок истории. Запрос с таймаутом возвращает `503 analytics_query_timeout`; уменьшите диапазон времени или кардинальность группировки перед повторной попыткой.
