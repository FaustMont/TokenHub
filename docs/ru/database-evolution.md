# Эволюция базы данных

TokenHub развивает базу данных с помощью явных, однонаправленных миграций. На этой странице описаны модель, команды обслуживания и взаимодействие обновлений и откатов с базой данных.

Эта страница является нормативным источником репозитория для жизненного цикла эволюции базы данных и контракта безопасности, реализованных в `backend/internal/dbschema`, CLI обслуживания, управляемых обновлениях и CI.

## Модель

- **Базовая линия внедрения.** Каждая база данных несёт реестр миграций (`schema_migrations`). Базы данных, созданные старыми релизами, внедряются при следующем запуске: поток замороженной схемы завершает их, они семантически проверяются по эталонному снимку, и записывается строка базовой линии. Свежие базы данных создаются из замороженного базового SQL, а не из потока ORM.
- **Расширяющие миграции** добавляют совместимую структуру и выполняются автоматически при запуске. **Сжимающие миграции** удаляют старую структуру и никогда не выполняются при запуске; они выполняются только через команду обслуживания с проверенными предусловиями.
- **Контрольные суммы и грязное состояние.** Контрольная сумма каждой применённой миграции проверяется при каждом запуске. Неудачная нетранзакционная миграция оставляет грязный маркер, который отказывает в запуске до устранения; неудачная транзакционная миграция откатывает только свою версию.
- **Заполнения данных** живут в собственном реестре (`data_backfills`). Блокирующие заполнения должны завершиться до того, как экземпляр сообщит о готовности; онлайн-заполнения выполняются в идемпотентных пакетах пока сервис продолжает обслуживать запросы, координируясь на уровне кластера через аренды, чтобы работа аварийно завершившегося исполнителя была возобновлена другим экземпляром.
- **Пульсы экземпляра.** Каждый работающий экземпляр публикует свой релиз с TTL. Обслуживание контрактов отказывается выполняться пока живы экземпляры со свежими пульсами.
- **Совместимость при откате.** Каждый релиз объявляет диапазон состояния базы данных, на котором он может полностью работать. Управляемый откат сначала выполняет только-читаемый предполётный контроль: релизы без проверенной записи совместимости отклоняются как `unknown`, а состояние базы данных вне диапазона целевого релиза отклоняется как `incompatible`. Административная консоль отмечает цели отката как совместимые с базой данных, несовместимые или неизвестные.

Готовность (`/readyz`, `/healthz`) не проходит, пока реестр грязный или непроверяемый или блокирующее заполнение не завершено. Ожидающие онлайн-заполнения никогда не влияют на готовность.

## Команды обслуживания

Главный бинарный файл поставляется с подкомандой `db`:

```bash
tokenhub db status                                  # реестр, заполнения, живые экземпляры
tokenhub db verify                                  # контрольные суммы реестра + семантическая проверка схемы
tokenhub db prepare                                 # совместимое с запуском внедрение + расширения, без обслуживания
tokenhub db migrate                                 # применить ожидающие расширяющие миграции
tokenhub db repair --version <n>                    # очистить грязную миграцию (только проверенное восстановление)
tokenhub db contract --dry-run                      # предполётный контроль сжимающей миграции
tokenhub db contract --backup-reference <ref> --maintenance
```

База данных разрешается из `TOKENHUB_DATABASE_URL` (или пути SQLite по умолчанию).

`contract` требует всего следующего перед выполнением чего-либо: все заполнения данных завершены, нет пульсов живых экземпляров, проверенная оператором ссылка на резервную копию и явное утверждение обслуживания. Для SQLite сначала создайте встроенную резервную копию; для PostgreSQL предоставьте ссылку на внешнюю резервную копию, которую вы сами проверили.

## Эксплуатационные примечания

- `tokenhub db migrate` для базы данных без базовой линии внедрения указывает на нормальный запуск сервера: внедрение происходит там, внутри сериализованного раздела схемы.
- Отказанный контракт сообщает, какое предусловие не выполнено; ничего не было выполнено.
- После отката к предыдущему релизу предыдущий релиз продолжает работать с текущей базой данных; когда более новый релиз возвращается, он повторно проверяет реестр и продолжает.
- Управляемое обновление запускает собственный бинарный файл целевого релиза против базы данных сначала: `db prepare` выполняет сериализованное, совместимое с запуском внедрение и поток расширения без публикации обслуживающего пульса, поэтому поддерживаемые до-реестровые базы данных могут быть подготовлены перед активацией; `db verify` затем семантически проверяет получившийся реестр и схему. Цель активируется только после прохождения обоих. Если активированный релиз затем не проходит первую загрузку, предыдущий релиз автоматически реактивируется один раз (только когда обновление не выполняло контракт и запись совместимости предыдущего релиза охватывает состояние базы данных); второй сбой останавливает переключение версий для восстановления оператором.
- Административная консоль показывает раздел эволюции базы данных только для чтения (версия состояния, готовность, диапазон совместимости, заполнения, живые экземпляры); операции контракта и восстановления — только CLI по дизайну.

## Для разработчиков

- Исполнитель миграций находится в `backend/internal/dbschema`. Замороженный базовый SQL встроен по диалектам в `backend/internal/dbschema/migrations/`.
- Регенерируйте базовый SQLite после изменений модели с `UPDATE_BASELINE=1 go test ./internal/server -run TestSQLiteBaselineSQLIsCurrent`; базовый PostgreSQL регенерируется аналогично с заданным `TEST_POSTGRES_URL` и тегом сборки `integration`. Тесты не проходят при устаревшем базовом.
- CI запускает интеграционный набор PostgreSQL и N-1 двусторонний контракт v0.4.0 на SQLite и PostgreSQL: старый бинарный файл создаёт базу данных, текущий релиз внедряет её и сообщает о готовности, старый бинарный файл снова загружается и выполняет API-контракт (аутентификация, проект, API-ключ, провайдер, модель и маршрут, один запрос шлюза и записи аудита), и текущий релиз возвращается и читает выбранные долговечные записи (проект и модель на обоих диалектах, плюс провайдер на SQLite). Отдельная ветка SQLite закрепляет реальную форму схемы v0.5.0, внедряет её и доказывает, что оба релиза могут загрузиться; она не запускает CRUD-контракт или ветку PostgreSQL v0.5.0. Зафиксированные неизменяемые фикстуры в `backend/internal/dbschema/fixtures/` охватывают v0.4.0 на обоих диалектах и v0.5.0 на SQLite; CI проверяет каждую охваченную базу данных с `go run ./cmd/n1check` перед внедрением.
- Регенерируйте встроенный манифест миграций после изменений реестра или базового с `go run ./cmd/manifestgen` из `backend/`; CI не проходит когда встроенная копия устарела.
